## פרויקט Firebase (נפרד מהחנות)

מגרסה 1.8.1 פרטי הפרויקט tizonfinance כתובים בקוד (`BUILT_IN_CLOUD` בתחילת App.jsx), וכל מכשיר מתחבר לענן לבד ומציג מסך כניסה. הפרטים האלה ציבוריים; את הנתונים מגנים הכניסה וחוקי Firestore. "עבודה בלי ענן" מנתק רק את המכשיר הזה, ובהגדרות יש "חזרה לענן".

1. console.firebase.google.com ← Add project ← `tizon-books`.
2. Authentication ← Sign-in method ← Email/Password ← Enable.
3. Firestore Database ← Create database.
4. Firestore ← Rules ← מדביקים את `firestore.rules` ← Publish.
5. Project settings ← Your apps ← Web ← מעתיקים את `firebaseConfig`.
6. במערכת: גיבוי וענן ← מדביקים ← חבר לענן ← "משתמש חדש".

## משתני סביבה ב-Netlify

Site configuration ← Environment variables ← Add a variable. אחרי ההוספה: Deploys ← Trigger deploy.

| משתנה | ערך |
|---|---|
| `BOOKS_PROJECT_ID` | מזהה פרויקט ה-Firebase, למשל `tizon-books` |
| `ALLOWED_EMAILS` | האימייל שלך (ומופרדים בפסיק, אם יש עוד) |
| `SIGN_P12_PASSWORD` | הסיסמה של תעודת החתימה |
| `SMTP_HOST` | ב-Gmail: `smtp.gmail.com` |
| `SMTP_PORT` | `465` |
| `SMTP_USER` | כתובת המייל השולחת |
| `SMTP_PASS` | ב-Gmail: "סיסמת אפליקציה" (חשבון Google ← אבטחה ← אימות דו-שלבי ← סיסמאות אפליקציה) |
| `MAIL_FROM` | למשל `Tizon Health <you@gmail.com>` |
| `SIGN_NAME` | לא חובה: השם שיופיע בחתימה |
| `ITA_CLIENT_ID` · `ITA_CLIENT_SECRET` | מספרי הקצאה: מהאפליקציה בפורטל המפתחים של רשות המסים (אחרי רישום התוכנה) |
| `ITA_REDIRECT_URI` | `https://<האתר>/.netlify/functions/books-mail?action=ita-callback`, בדיוק כפי שנרשם בפורטל |
| `ITA_ENV` | `sandbox` לבדיקות (ברירת מחדל), `production` לייצור |
| `ITA_SCOPE` | ה-scope שהפורטל נתן לאפליקציה (ברירת מחדל: `scope`) |
| `FIREBASE_SERVICE_ACCOUNT` | לא חובה: מפתח השירות כ-base64. בדרך כלל מעלים אותו מהמערכת (גיבוי וענן ← דפי סליקה) |

## תעודת חתימה

1. רוכשים תעודה לחתימה אלקטרונית מאובטחת מגורם מאשר (למשל קומסיין), כקובץ `.p12` או `.pfx`.
2. מגדירים ב-Netlify את `SIGN_P12_PASSWORD` ואת `ALLOWED_EMAILS`, ומפעילים Trigger deploy.
3. במערכת: גיבוי וענן ← חתימה דיגיטלית ושליחה ← העלה תעודה.

כל הסימונים בכרטיס צריכים להיות ✓. מאותו רגע יופיעו ליד כל מסמך הכפתורים "PDF חתום" ו"שלח חתום".

## מסמכים

- **ניסיון** (ברירת מחדל): מספרי T-, סימן מים, לא נספר כהכנסה.
- **אמיתי**: רק בענן, אחרי סימון "רואה החשבון אישר". מספור רץ, בלי עריכה ובלי מחיקה (נאכף גם בחוקי Firestore).

## ייבוא מ-iCount

1. ב-iCount: מערכת ← ייצוא במבנה אחיד ← יצירת קבצים במבנה אחיד ← מהיום הראשון ועד היום.
2. במערכת: בעסק המתאים ← לשונית "ייבוא" ← "ייבוא מ-iCount" ← בוחרים את קובץ ה-ZIP כמו שהוא.
3. בודקים את התצוגה המקדימה ← ייבא.

המסמכים נשמרים כהיסטוריה לקריאה בלבד, עם המספרים של iCount, ונספרים בהכנסות ובמע״מ. חשבוניות רכש נכנסות כהוצאות. הרצה חוזרת מוסיפה רק מה שחדש. הזמנות מהחנות שהחשבונית שלהן הופקה ב-iCount נספרות פעם אחת.

## לקוחות

בכל עסק ← לשונית "לקוחות":
- **ייבוא מ-iCount:** ב-iCount לקוחות ← ייצוא לאקסל, ואז כאן "ייבוא מ-iCount (אקסל / CSV)". העמודות מזוהות לבד, ואפשר לתקן.
- **סנכרון מהחנות:** בעסק שמקושר לחנות מופיע כמה לקוחות חדשים יש בחנות, וכפתור "סנכרן מהחנות".
- **שליחה לחנות:** לקוחות שיש כאן ואין בחנות: "שלח לחנות…", בוחרים מי, ומאשרים שהסכימו לדיוור (רשימת הלקוחות של החנות היא גם רשימת הדיוור שלה). נוצרים בחנות רק לקוחות חדשים; קיימים לא משתנים. זו הכתיבה היחידה של המערכת לחנות.
- לקוח מכל מסמך שמופק נכנס לרשימה לבד. ייבוא מסמכים מ-iCount מביא גם את הלקוחות שלהם.
- אותו לקוח משני מקורות מאוחד לפי ח.פ., אימייל או טלפון. פרטים קיימים לא נדרסים.

## פריטים

בכל עסק ← לשונית **פריטים**: שם, מק״ט, מחיר (כולל מע״מ או לפניו), יחידה וקטגוריה. ייבוא מ-iCount: פריטים ← ייצוא לאקסל, ומעלים כאן (XLSX או CSV). פריט מזוהה לפי מק״ט, ובלעדיו לפי השם.
בחשבונית ובדף סליקה בוחרים פריט מהרשימה, והמחיר נכנס לבד ומומר לפי "המחירים כוללים מע״מ".

## דפי סליקה (זד קרדיט)

שולחים ללקוח קישור קצר (`/p/...`). כשהוא פותח אותו, השרת יוצר עמוד תשלום של זד קרדיט. אחרי חיוב מוצלח:
1. זד קרדיט מודיעה לשרת. הכתובת כוללת סוד שנשמר רק בשרת.
2. השרת בודק שהסכום תואם ושהדף עדיין פתוח, ומפיק בטרנזקציה אחת **חשבונית מס קבלה** (לעוסק פטור: **קבלה**) במספר הבא ברצף, מסמן את הדף "שולם" ורושם ביומן.
3. ה-PDF נחתם ונשלח ללקוח במייל. מי שיצר את הדף מקבל הודעה.

תשלום כפול על אותו דף לא מפיק מסמך נוסף: הוא נרשם כ"שולם פעמיים · לזכות", ונשלחת הודעה.

**הגדרה (פעם אחת), גיבוי וענן ← דפי סליקה:**
1. **מפתח שירות של Firebase:** בקונסולה ← Project settings ← Service accounts ← Generate new private key ← מעלים את הקובץ כאן. הוא נשמר רק ב-Netlify Blobs של האתר.
2. **מפתח זד קרדיט (WebCheckout)** לכל עסק.

כדי שהמסמך יישלח ללקוח לבד, צריך גם תעודת חתימה וגם SMTP. מפרסמים גם את `firestore.rules` של הגרסה.

## משתמשים והרשאות

תפריט הצד ← "משתמשים והרשאות" (לבעלים, בענן): בעלים · מפיק מסמכים (מסמכים ולקוחות בלבד) · צפייה בלבד (רואה חשבון). אחרי ההוספה נפתח מייל הזמנה מוכן. המשתמש נרשם ב"משתמש חדש" באותו אימייל.
נעילה במכשיר: גיבוי וענן ← "נעילה במכשיר הזה" ← קוד 4–8 ספרות. ננעל שוב אחרי 15 דקות בלי פעילות.

## רשות המסים

בכל עסק ← לשונית "רשות המסים":
- ייצוא **מבנה אחיד** (INI.TXT + BKMVDATA.TXT, הוראה 1.31).
- פלט סיכום לרישום התוכנה.
- יומן פעולות.

את הקבצים בודקים בסימולטור של רשות המסים לפני שמגישים בקשת רישום.

- **רשומות הנהלת חשבונות (B100/B110):** סימון בלשונית "רשות המסים". פקודות יומן כפולות וכרטסת, עם בדיקת מאזן.
- **ארכיון חודשי:** בתחילת כל חודש נשלח למייל (בענן עם מייל) קובץ עם מבנה אחיד של החודש שעבר וגיבוי מלא. אפשר גם להוריד ידנית: גיבוי וענן ← ארכיון חודשי.
- **מספרי הקצאה אוטומטיים:** אחרי הגדרת `ITA_*` ← גיבוי וענן ← "התחבר לרשות המסים" לכל עסק (פעם בשלושה חודשים). מאז חשבונית שצריכה מספר מקבלת אותו מיד אחרי ההפקה.
- **מזומן:** מעל התקרה (עד ₪6,000; מעל זה, הנמוך מבין ₪6,000 ל-10% מהעסקה) מסמך אמיתי נחסם.

## הדרכה

- בכל מסך יש סיור קצר. הוא רץ לבד בפעם הראשונה שנכנסים למסך.
- אחרי עדכון: חלון "מה חדש" מופיע פעם אחת, ובכל מסך שהשתנה רץ סיור רק על מה שחדש (מסומן "חדש").
- הכפתור **?** בפינה מפעיל שוב את הסיור של המסך. דף **מדריך** בתפריט: כל הסיורים, כיבוי והפעלה של ההדרכה האוטומטית, ורשימת השינויים.
- מקלדת: חצים לשלב הבא או הקודם, Esc לסגירה.

למפתח: כל שלב מצביע על אלמנט עם `data-tour="…"` ומסומן בגרסה שבה נוסף (`since`). לפני כל build רץ `tour-check.mjs`, והוא עוצר את הבנייה אם שלב מצביע על אלמנט שכבר לא קיים, אם לשונית בלי סיור, או אם לגרסה החדשה אין שורה ב-`CHANGES`. כך ההדרכה לא יכולה לפגר אחרי המערכת: עדכון שמשנה מסך מחייב לעדכן גם את הסיור שלו.
